pickle — 직렬화 · 역직렬화

개념

프로그램이 끝나면 메모리 속 변수는 사라집니다. 직렬화(dump)는 파이썬 객체를 파일로 저장 가능한 바이트로 바꾸는 것, 역직렬화(load)는 그 바이트를 다시 원래 객체로 복원하는 것입니다. pickle은 거의 모든 파이썬 객체를 그대로 저장하지만 결과물이 사람이 못 읽는 바이너리라서, 신뢰 못 하는 pickle 파일은 절대 열면 안 됩니다.

bigpy01.py쓰기
import pickle

f = open('setting.txt', 'wb')   # wb = write binary, 항상 이 모드
setting = [{'title': 'python program'}, {'author': 'soldesk'}]
pickle.dump(setting, f)
f.close()
bigpy02.py읽기
f = open('setting.txt', 'rb')   # rb = read binary
setting = pickle.load(f)
f.close()
함수대상
dump() / load()파일 객체를 직접 넘길 때
dumps() / loads()메모리상 bytes를 직접 다룰 때 (s = string)

json — 직렬화 · 역직렬화

개념

pickle과 같은 개념이지만, 저장 형태가 사람이 읽는 텍스트이고 거의 모든 언어·웹 API가 공통으로 쓰는 표준 포맷입니다. 대신 dict/list/str/숫자 같은 기본 타입만 다룹니다 — 크롤링 결과 저장에 가장 많이 씁니다.

picklejson
직렬화pickle.dump(obj, f)json.dump(obj, f)
역직렬화(파일)pickle.load(f)json.load(f)
역직렬화(문자열)pickle.loads(b)json.loads(s)
형태바이너리텍스트
json06.py
data = {}
data['people'] = []
data['people'].append({'name': 'kim', 'grade': [95, 77, 89]})

with open('member.json', 'w') as f:
    json.dump(data, f, ensure_ascii=False, indent=2)  # 한글 안 깨지게 + 들여쓰기

with open('member.json', 'r') as f:
    r = json.load(f)
    for p in r['people']:
        print(p['name'])
load() vs loads() — load(파일객체)는 파일을 직접 넘겨서 역직렬화, loads(문자열)은 이미 .read()로 읽은 문자열을 역직렬화(s=string). API 응답처럼 이미 문자열이면 loads()를 씁니다. requests의 .json()은 이 과정을 대신 해주는 것입니다.

openpyxl — 엑셀 쓰기 · 읽기

개념

Workbook(파일 전체) 안에 여러 Worksheet(시트)가 있고, 셀은 cell(row=, column=)으로 접근합니다. 엑셀 좌표는 1부터 시작이라, 0-based인 enumerate 인덱스엔 항상 +1이 필요합니다.

bigpy04.py쓰기
wb = openpyxl.Workbook()
sheet = wb.active
sheet.title = '회원정보'

for idx, title in enumerate(header_titles):
    sheet.cell(row=1, column=idx+1, value=title)   # idx+1: 엑셀은 1부터

wb.save('members.xlsx'); wb.close()
bigpy05.py읽기
wb = openpyxl.load_workbook('sample.xlsx')
sheet = wb['Sheet1']

for row in sheet.iter_rows(min_row=2):   # 2행부터(헤더 제외), 가장 일반적인 순회방식
    for cell in row:
        print(cell.value)
wb.close()
✗ 행 번호를 반복문 밖에서 한 번만 정하고 안에서 안 늘리면 여러 행이 같은 위치에 덮어써집니다. row_num += 1처럼 매번 늘려야 합니다.

pandas — CSV 읽기 옵션

개념

실제 CSV는 위에 제목 줄이 껴있거나 헤더가 없기도 합니다. 아래 옵션들은 서로 독립적이라 조합을 정확히 맞춰야 합니다.

옵션의미
skiprows=[n]리스트 → 그 인덱스 줄만 제외
skiprows=n정수 → 맨 앞 n줄 제외
header=None어떤 줄도 컬럼명으로 안 씀
names=[...]컬럼명 직접 지정 (헤더 줄을 자동으로 없애주진 않음)
index_col=[n]n번째 컬럼을 행 인덱스로
csv01.py
from pathlib import Path
BASE_DIR = Path(__file__).resolve().parent
df = pd.read_csv(BASE_DIR/"csv_s1.csv", skiprows=2, header=None,
                  names=["Month", 2023, 2024, 2025], index_col=[0])
✗ names=[...]는 "헤더가 없다 치고 새 이름표만 붙이는 것"이라, 원래 헤더 텍스트 줄이 데이터로 그대로 남을 수 있습니다. skiprows로 그 줄까지 물리적으로 걷어내야 합니다.
상대경로 문제 — 상대경로는 스크립트 위치가 아니라 터미널 cwd 기준입니다. Path(__file__).resolve().parent로 절대경로를 고정하면 어디서 실행하든 항상 스크립트 옆 파일을 찾습니다. (chapter04 이후 거의 모든 파일이 이 패턴을 씁니다.)

★ 저장 직전에 항상 갈리는 선택

결과를 파일로 저장하기 — txt · CSV · JSON · 엑셀

지금까지 pickle·json·openpyxl을 각각 따로 배웠는데, 막상 "이 결과를 어떤 파일로 저장하지?"를 고를 때는 네 가지를 한 번에 놓고 비교해야 헷갈리지 않습니다. 같은 데이터를 형식 4개로 각각 저장하는 코드를 나란히 뒀습니다 — 코드가 왜 조금씩 달라지는지 그 차이만 보면 됩니다.

사고 흐름
  1. 저장할 결과가 book_result = [{"제목":"A", "가격":"£51.77", "별점":"Three"}, ...]처럼 list[dict] 모양이라고 하자.
  2. 이걸 사람이 엑셀에서 열어보거나 표로 정렬해서 볼 거라면 → 한 줄(row)에 필드 여러 개가 나란히 있어야 하니 CSV가 자연스럽다.
  3. 이 결과를 다른 프로그램이 다시 읽어서 dict로 그대로 복원해 쓸 거라면(중첩 구조가 있다면 특히) → 모양을 안 망가뜨리는 JSON이 낫다.
  4. 서식(색·병합·여러 시트)까지 필요하거나 이미 pandas로 분석 중이었다면 → 엑셀로 바로 뽑는다.
  5. 값이 제목처럼 필드 하나뿐인 list[str]이라면 → 애초에 표가 필요 없으니 txt 한 줄씩이 제일 간단하다.
→ 즉 "필드가 하나냐 여러 개냐"와 "사람이 볼 거냐, 프로그램이 다시 읽을 거냐" 두 질문이 형식을 정한다.
형식어울리는 자료구조핵심 코드필수 옵션언제
txtlist[str] (필드 1개)f.write(값+"\n")encoding="utf-8"제목만, 로그처럼 단순 텍스트
CSVlist[dict] (레코드 여러 개)csv.DictWriternewline="", encoding="utf-8-sig"엑셀로 열어볼 정형 데이터
JSONdict, list[dict], 중첩 구조json.dump(...)ensure_ascii=False, indent=2구조 그대로 보존, 나중에 다시 읽어 쓸 데이터
엑셀list[dict] / DataFramedf.to_excel() 또는 openpyxlindex=False, pip install openpyxl서식·여러 시트·차트 필요할 때

같은 데이터, 형식 4개로 저장 — 코드 비교

① txt — 필드 하나(list[str])일 때
titles = ["A Light in the Attic", "Tipping the Velvet", "Soumission"]

with open("titles.txt", "w", encoding="utf-8") as f:
    for t in titles:
        f.write(t + "\n")   # \n을 직접 안 붙이면 한 줄에 다 붙어버림
② CSV — 레코드 여러 개(list[dict])일 때가장 흔한 크롤링 저장
import csv

book_result = [
    {"제목":"A Light in the Attic", "가격":"£51.77", "별점":"Three"},
    {"제목":"Tipping the Velvet", "가격":"£53.74", "별점":"One"},
]

with open("books.csv", "w", newline="", encoding="utf-8-sig") as f:
    writer = csv.DictWriter(f, fieldnames=["제목", "가격", "별점"])
    writer.writeheader()
    writer.writerows(book_result)   # dict의 key가 fieldnames와 정확히 같아야 함
CSV인데 필드가 하나뿐인 list[str]을 저장하고 싶다면 DictWriter 대신 더 단순한 csv.writer로 충분합니다: writer = csv.writer(f); writer.writerow(["제목"]); [writer.writerow([t]) for t in titles].
③ JSON — 구조를 그대로 보존할 때중첩도 그대로 유지됨
import json

with open("books.json", "w", encoding="utf-8") as f:
    json.dump(book_result, f, ensure_ascii=False, indent=2)
    # book_result가 list[dict]든 dict든 중첩 dict든, 모양 그대로 저장됨
④ 엑셀 — pandas 버전(짧음) vs openpyxl 버전(서식 제어)
import pandas as pd
df = pd.DataFrame(book_result)
df.to_excel("books.xlsx", index=False, sheet_name="Sheet1")   # index=False 없으면 왼쪽에 0,1,2... 컬럼이 하나 더 생김

# -- 서식(굵게, 셀 배경색 등)까지 직접 다뤄야 하면 openpyxl로 한 셀씩 --
import openpyxl
wb = openpyxl.Workbook()
sheet = wb.active
sheet.append(["제목", "가격", "별점"])           # 헤더 행
for b in book_result:
    sheet.append([b["제목"], b["가격"], b["별점"]])
wb.save("books.xlsx")

형식별로 꼭 걸리는 실수

✗ txt에 f.write(t)만 하고 "\n"을 안 붙이면 모든 제목이 줄바꿈 없이 한 줄로 다 이어붙습니다.
✗ CSV에서 newline=""를 빼먹으면 윈도우에서 매 줄 사이에 빈 줄이 하나씩 더 생깁니다. encoding="utf-8-sig"를 안 쓰면 엑셀에서 한글이 깨져 보입니다(메모장으로 보면 멀쩡한데 엑셀에서만 깨지는 게 이 문제의 특징).
✗ JSON에서 ensure_ascii=False를 빼먹으면 한글이 \uXXXX 코드로 저장됩니다(파일은 정상이지만 사람이 못 읽음). json.dump는 dict/list/str/숫자/불리언만 저장 가능 — 커스텀 클래스 객체를 그대로 넣으면 TypeError.

개념

클릭한다고 다음 페이지가 바로 완성되지 않습니다. 처음엔 무조건 몇 초 기다리는 time.sleep을 쓰지만, 느린 날엔 부족하고 빠른 날엔 낭비입니다. WebDriverWait는 "이 조건이 참이 될 때까지만" 기다려 더 안정적입니다.

사고 흐름
  1. 로그인 버튼을 클릭한 다음 무슨 일이 벌어지는지 생각해본다 — 페이지 이동, 새 DOM 로딩, 네트워크 요청까지 걸리는 시간은 매번 다르다.
  2. 일단 time.sleep(3)으로 3초를 준다 — 로컬에서 몇 번 돌려보니 되는 것 같다.
  3. 근데 이 3초라는 숫자가 어디서 왔는지 자문해본다 — 방금 내 네트워크 속도로 몇 번 테스트해본 값일 뿐, 서버가 느린 날이나 다른 PC에서 돌릴 땐 근거가 없다.
  4. 더 큰 문제도 보인다 — 3초보다 빨리 끝나도 코드는 그대로 3초를 낭비하고, 3초보다 느리면 아직 없는 요소를 찾다가 예외가 난다. "고정된 시간"과 "실제로 준비됐는지"는 다른 것이다.
  5. 그러면 진짜 필요한 건 시간이 아니라 조건이다 — "이 요소가 DOM에 나타날 때까지"를 코드로 표현할 방법을 찾는다.
  6. WebDriverWait + expected_conditions가 정확히 그 역할이다 — 조건이 참이 될 때까지만 기다리고, 끝내 안 되면 타임아웃으로 명확하게 실패한다.
→ email = wait.until(EC.presence_of_element_located(...))처럼, "몇 초 기다릴지"가 아니라 "무엇이 준비됐는지"를 조건으로 건다.

콤보 패턴 — 목록은 브라우저로, 파일은 requests로

1브라우저로 렌더
2src 주소만 수집
3requests.get().content
4파일로 저장
개념

<img src="...">의 src는 이미지가 어디 있는지 알려주는 주소 문자열일 뿐, 이미지 파일 자체가 아닙니다. 브라우저는 이 주소를 보고 알아서 그려주지만, 우리 코드는 주소 텍스트만 손에 쥔 상태입니다.

사고 흐름
  1. 브라우저로 검색 결과 페이지를 열면 이미지가 화면에 잘 보인다 — "다 보이니까 이미 다 있는 거 아닌가" 하는 생각이 먼저 든다.
  2. 근데 화면에 보이는 건 브라우저가 <img src="...">를 읽고 그 주소로 따로 요청을 보내 그린 결과다 — 페이지 자체엔 파일이 없고 "어디 있는지 알려주는 주소 문자열"만 있다.
  3. page.query_selector_all("img")로 얻는 것도 마찬가지다 — img.get_attribute("src")는 문자열 하나일 뿐, 그 문자열을 그냥 파일에 써봐야 이미지가 생기지 않는다.
  4. 그러면 "주소를 안다"와 "파일을 갖고 있다" 사이에 한 단계가 더 필요하다는 게 보인다 — 그 주소로 새로운 요청을 한 번 더 보내야 진짜 바이트가 온다.
  5. 미리보기 이미지는 data:image/...로 오기도 한다는 것도 이 시점에 같이 정리된다 — http로 시작하는 진짜 주소만 걸러야 한다.
  6. 결론적으로 브라우저 단계(주소 수집)와 requests 단계(다운로드)는 하나의 반복문으로 합칠 게 아니라 분리해야 한다 — 브라우저를 계속 띄워둔 채로 매번 다운로드까지 하면 느리고 불안정하다.
→ 1단계에서 urls 리스트를 다 모은 뒤, 2단계에서 따로 반복문을 돌며 requests.get(url).content로 바이트를 받아 파일에 쓴다.
img03.py 형태Playwright + requests
with sync_playwright() as p:
    browser = p.chromium.launch(headless=False)
    page = browser.new_page()
    page.goto(SEARCH_URL); page.wait_for_timeout(3000)

    imgs = page.query_selector_all("img")
    urls = [img.get_attribute("src") for img in imgs]
    urls = [u for u in urls if u and u.startswith("http")]  # data: 미리보기 제외
    browser.close()

# 주소를 안다고 파일이 저장되는 게 아니라, 그 주소로 새 요청을 한 번 더
for i, url in enumerate(urls[:20], start=1):
    data = requests.get(url, timeout=5).content   # .content = 바이너리 그대로
    with open(f"{i}.jpg", "wb") as f:
        f.write(data)

problem 폴더는 지금 직접 푸는 중이라 여기엔 넣지 않았습니다. 대신 자료구조 선택 기준 다섯 가지 상황을 각각 정면으로 다루는 새 문제 5개를 코드까지 적어뒀습니다 — "아, 이런 상황엔 이렇게 가야 하는구나"를 코드로 확인하는 용도입니다. 전부 안정적인 연습용 사이트(quotes.toscrape.com, jsonplaceholder.typicode.com)를 씁니다.

문제 1

명언 사이트에서 저자 이름만, 중복 없이 뽑아 텍스트로 저장

자료구조 포인트 — 값이 author 하나뿐이라 딕셔너리가 필요 없습니다. 게다가 "중복 없이"이므로 set으로 걸러낸 뒤 list로 바꿔 저장합니다.

https://quotes.toscrape.com/ 첫 페이지에 있는 명언들의 저자 이름만 중복 없이 모아 authors.txt에 한 줄씩 저장하세요.

사고 흐름
  1. 문제를 다시 읽는다 — "저자 이름만", "중복 없이", "텍스트로 저장". 뽑을 값이 author 하나뿐이라는 게 먼저 눈에 띈다.
  2. 값이 하나뿐이면 레코드에 필드가 여러 개인 상황이 아니다 — dict를 쓸 이유가 없다(키에 붙일 다른 값이 없다).
  3. "중복 없이"를 어떻게 만족시킬지 생각한다 — 다 모은 뒤에 걸러내는 것보다, 애초에 중복을 허용 안 하는 자료구조에 넣으며 모으는 게 더 간단하다.
  4. set이 정확히 그 역할이지만, set은 순서가 없다는 것도 같이 떠오른다 — "파일로 저장"한다는 요구를 생각하면 실행할 때마다 순서가 바뀌는 건 곤란하다.
  5. 그래서 모을 땐 set, 저장 직전엔 정렬해서 list로 바꾼다는 두 단계로 나뉜다.
→ author_set = set()에 add()로 모으고, sorted(author_set)로 list로 바꿔 한 줄씩 파일에 쓴다.
practice01.pylist[str] + set 중복제거
import requests
from bs4 import BeautifulSoup
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent
url = "https://quotes.toscrape.com/"

res = requests.get(url)
soup = BeautifulSoup(res.text, "html.parser")

# 값이 이름 하나뿐 -> dict 필요 없음. 리스트로 충분.
# 다만 저자가 여러 명언에 반복 등장하므로 set으로 먼저 중복 제거
author_set = set()
for small in soup.select(".quote .author"):
    author_set.add(small.get_text(strip=True))

authors = sorted(author_set)   # set은 순서가 없어서, 저장 전에 정렬해서 결과를 예측 가능하게

with open(BASE_DIR / "authors.txt", "w", encoding="utf-8") as f:
    for name in authors:
        f.write(name + "\n")

print(f"{len(authors)}명 저장 완료")
만약 저자별로 "명언 몇 개 썼는지" 개수까지 알고 싶다면 얘기가 달라집니다 — 그건 이름(key)마다 숫자(value)가 필요하니 dict로 (Counter가 정확히 이 모양입니다). "값 하나만 모으면 끝"이면 list, "이름에 뭔가를 붙여야" 하면 dict — 이 문제와 문제 3의 차이가 그 경계선입니다.
문제 2

명언 10개의 텍스트·저자·태그 개수를 CSV로

자료구조 포인트 — 레코드(명언 하나)가 필드 3개를 갖고, 그 레코드가 10개 있습니다. 크롤링에서 가장 흔한 list[dict] + DictWriter 패턴입니다.

같은 페이지에서 명언 10개의 (본문 텍스트, 저자, 태그 개수)를 크롤링해 quotes.csv로 저장하세요.

사고 흐름
  1. 문제를 뜯어본다 — "명언 10개"(레코드가 여러 개), "텍스트·저자·태그 개수"(레코드 하나에 필드가 세 개). 이 둘이 동시에 참이다.
  2. 필드가 여러 개인 레코드가 여러 개 있으면, 레코드 하나는 dict, 그게 여러 개 모이면 list — 그래서 list[dict]가 바로 떠오른다.
  3. 나중에 이 데이터로 뭘 하는지 확인한다 — "CSV로 저장"이 전부다. 특정 명언 하나를 이름으로 즉시 찾아야 하는 요구는 없다.
  4. 즉시 조회 요구가 없으니 딕셔너리 하나로 모으는 방식을 쓸 이유가 없다 — 오히려 본문 텍스트를 key로 쓰면 너무 길고 어색하다.
  5. "CSV로 저장"이라는 조건에서 csv.DictWriter가 list[dict]를 그대로 받는다는 걸 떠올리면, 애초에 결과를 그 모양으로 모아두는 게 저장 단계까지 자연스럽게 이어진다는 게 확인된다.
→ results = []로 시작해서 반복문 안에서 select_one()으로 필드 세 개를 뽑아 dict로 묶어 append하고, 끝나면 writer.writerows(results)로 한 번에 CSV에 쓴다.
practice02.pylist[dict] + csv.DictWriter
import csv

quotes = soup.select(".quote")[:10]
results = []   # list[dict]로 시작 -- 여러 필드 레코드가 여러 개

for q in quotes:
    text = q.select_one(".text").get_text(strip=True)
    author = q.select_one(".author").get_text(strip=True)
    tag_count = len(q.select(".tags .tag"))   # select()는 리스트 -> len()으로 개수만

    results.append({
        "text": text,
        "author": author,
        "tag_count": tag_count,
    })

with open(BASE_DIR / "quotes.csv", "w", newline="", encoding="utf-8-sig") as f:
    writer = csv.DictWriter(f, fieldnames=["text", "author", "tag_count"])
    writer.writeheader()
    writer.writerows(results)   # results가 list[dict]라 바로 넘길 수 있음
✗ results = {}로 시작해서 results[text] = {...}처럼 담고 싶어질 수 있지만, 여긴 "빠르게 조회할 고유 키"가 없습니다(본문 텍스트를 key로 쓰면 너무 김). 순서대로 다 저장하고 끝인 상황이면 dict를 고를 이유가 없습니다.

자료구조 포인트 — 결과가 레코드 하나뿐입니다. list[dict]로 만들면 results[0]["email"]처럼 불필요한 인덱싱이 생깁니다 — dict 하나로 충분합니다.

https://jsonplaceholder.typicode.com/users/1에서 이름·이메일·회사명·도시만 뽑아 user_profile.json으로 저장하세요.

사고 흐름
  1. 문제를 본다 — "유저 한 명의 프로필만". 조회 대상이 정확히 하나다.
  2. API 응답도 확인한다 — /users/1은 유저 배열이 아니라 유저 객체 하나를 바로 준다. 이미 감쌀 리스트가 없는 형태다.
  3. 레코드가 하나뿐이면 list[dict]로 만들 이유가 없다 — 굳이 감싸면 이후 코드에서 항상 results[0]["email"]처럼 의미 없는 인덱스 0을 붙여야 한다.

문제 4

유저 10명을 모으되, username으로 즉시 조회 가능하게

자료구조 포인트 — 이번엔 레코드가 10개지만, 목적이 "전체를 훑는 것"이 아니라 "이름 하나로 바로 찾는 것"입니다. list[dict]로 모으면 매번 반복문이 필요하지만, username을 key로 쓴 dict면 즉시 조회됩니다.

https://jsonplaceholder.typicode.com/users(10명)를 조회해서, username으로 즉시 이메일을 찾을 수 있는 구조로 저장하세요. 그리고 "Bret"의 이메일을 반복문 없이 출력하세요.

사고 흐름
  1. 문제를 다시 읽는다 — "유저 10명"(레코드 여러 개)까지는 문제 2와 같다. 그런데 "username으로 즉시 조회", "반복문 없이 출력"이 추가로 붙는다.
  2. 레코드가 여러 개라고 해서 자동으로 list[dict]는 아니다 — "여러 개를 어떻게 다룰 것인가"가 진짜 기준이라는 걸 다시 떠올린다.
  3. 일단 list[dict]로 모았다고 가정하고 "Bret의 이메일"을 어떻게 꺼낼지 시뮬레이션해본다 — next(u for u in users if u["username"]=="Bret") 같은 반복 탐색이 매번 필요하다. 문제가 요구한 "반복문 없이"에 이미 어긋난다.
  4. username이 사람마다 겹치지 않는 고유값이라는 것도 확인한다 — 고유값이 있고 그걸로 즉시 찾아야 한다는 조건이 겹치면, 그게 바로 dict의 key로 쓰기 좋은 조건이다.
  5. 결론: username을 key로 쓰는 dict로 모은다 — 저장도 list가 아니라 그 dict를 그대로 json.dump한다.
→ users = {}로 시작해서 users[u['username']] = {...}로 채우고, users['Bret']['email']처럼 반복문 없이 바로 꺼낸다.

문제 5

여러 페이지를 넘겨가며 중복 없이 계속 쌓기

자료구조 포인트 — 무한스크롤과 같은 마음가짐입니다: "이미 모은 것"과 "새로 온 것"을 구분해서 중복 없이 누적하고, 더 이상 새 게 없으면 멈춥니다. 정적 페이지네이션으로 같은 패턴을 먼저 연습해두면 스크롤 버전(Playwright)으로 옮길 때 로직은 그대로 재사용됩니다.

quotes.toscrape.com은 /page/1/, /page/2/... 형태로 다음 페이지를 제공합니다. 페이지를 넘기며 명언 텍스트를 중복 없이 계속 모으다가, 새로 추가된 게 없는 페이지가 나오면 멈추고 총 개수를 출력하세요.

사고 흐름
  1. 문제를 본다 — "여러 페이지를 넘겨가며", "중복 없이", "새로 추가된 게 없는 페이지가 나오면 멈춘다". 세 가지 요구가 각각 다른 걸 요구한다.
  2. 최종 결과는 순서가 있는 목록(모은 명언들)이니 담는 그릇은 list다 — 여기까진 문제 2와 같다.
  3. "중복 없이"를 list만으로 확인하려면 매번 in collected로 전체를 훑어야 해서, 페이지가 늘어날수록 느려진다 — 조회 전용으로 훨씬 빠른 set을 하나 더 두면 이 문제가 사라진다.
  4. "새로 추가된 게 없으면 멈춘다"는 종료 조건을 코드로 어떻게 표현할지 생각한다 — 한 페이지를 처리하는 동안 새로 들어온 개수를 세어두면, 그 값이 0인지로 바로 판단할 수 있다.
  5. 페이지 자체가 존재하지 않는 경우(마지막 페이지 다음)도 있을 수 있으니, 명언 목록 자체가 비어있는 경우도 별도로 걸러야 무한루프를 막는다.
  6. 정리하면 세 가지 상태를 각각 다른 변수로 나눠 관리해야 한다는 게 확정된다 — 결과(list), 중복확인(set), 종료판단(개수).
→ collected는 list로 결과를 쌓고, seen은 set으로 중복만 빠르게 확인하고, 페이지마다 new_count가 0이면 while 루프를 break한다.
practice05.py누적 리스트 + set 중복확인 + 종료조건
collected = []          # 최종 결과 (순서 유지가 필요하니 list)
seen = set()            # "이미 모았는지" 빠르게 확인만 하는 용도 (조회 전용이라 set)
page = 1

while True:
    res = requests.get(f"https://quotes.toscrape.com/page/{page}/")
    soup = BeautifulSoup(res.text, "html.parser")
    texts = [q.select_one(".text").get_text(strip=True) for q in soup.select(".quote")]

    if not texts:            # 그 페이지 자체가 비어있음 -> 마지막 페이지 넘어감
        break

    new_count = 0
    for t in texts:
        if t not in seen:      # 스크롤 패턴의 "높이가 같으면 종료"와 같은 역할
            seen.add(t)
            collected.append(t)
            new_count += 1

    print(f"page {page}: 새로 {new_count}개, 누적 {len(collected)}개")

    if new_count == 0:        # 이번 페이지에서 하나도 새로 안 들어왔으면 그만
        break
    page += 1

print(f"총 {len(collected)}개 수집 완료")
왜 collected(list)와 seen(set) 둘 다 필요한가 — seen은 "이미 있는지"만 빠르게 확인하는 용도(순서 필요 없음, in 검사가 리스트보다 훨씬 빠름), collected는 실제로 저장해서 나중에 쓸 순서 있는 결과입니다. Playwright 무한스크롤도 구조는 똑같습니다 — while 대신 "스크롤→대기", texts가 비었는지 대신 "페이지 높이가 그대로인지"로 종료 조건만 바뀝니다.
